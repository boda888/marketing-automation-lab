- 2026-11-13 · ops-db · Supabase as the ops table: put a UNIQUE constraint on the natural key (`domain`, lowercased `email`) and write from n8n / Clay's HTTP API column with `POST /rest/v1/<table>?on_conflict=<key>` + `Prefer: resolution=merge-duplicates,return=representation` — the stock n8n Supabase node has no upsert and its Create sends every input item in one request, so a re-run either errors on duplicates or loses the whole batch on one bad row. Source: research/notes/2026-11-13-R1-supabase-ops-db-clay-n8n.md (n8n `Supabase.node.ts`, PostgREST docs)
- 2026-11-13 · ops-db · Run Remove Duplicates on the conflict key before every Supabase upsert and send chunks of 200–500: two rows with the same key in one request raise a Postgres cardinality violation and PostgREST rolls back the entire request; route failed chunks to a one-row-at-a-time retry to find the bad row. On Get Many always set Order By (offset paging has no default order) — Return All stops after any page with < 1,000 rows. Source: same note (PostgreSQL `insert.sgml`, PostgREST `transactions.rst`)
- 2026-11-12 · n8n · Add **Batching** explicitly on every HTTP Request node that writes to a vendor (sequencer add-lead, CRM upsert, Clay webhook, LLM): without it the node fires a request for every input item at the same moment, and with it the default is 50 requests started per second regardless of answers. Set Items per Batch = 1 and Batch Interval = 1,000 ÷ allowed req/s (+ margin), turn on continue-on-fail and send only the `429` items through a Wait (≥ the vendor's window) back into the call — Retry On Fail would re-send the leads that already went through, and the node never reads `Retry-After`. Source: research/notes/2026-11-12-R9-n8n-rate-limits-queue-mode.md (`HttpRequestV3.node.ts`)
- 2026-11-12 · n8n · Pacing in n8n is per execution: two workflows on one Smartlead / HubSpot key, overlapping schedule runs or queue-mode workers (10 parallel jobs each by default) multiply the rate. Funnel all pushes for one API key through a single queue workflow, or gate them on a Redis counter whose **key contains the window** (`smartlead:{{ $now.toFormat('yyyy-MM-dd HH:mm') }}`) — the Redis node's Increment + Expire resets the TTL on every call, so a plain "per-minute" key never expires under steady traffic and blocks forever; the node also replaces the lead item with `{key: count}`, so merge the lead back afterwards. Source: same note (`Redis.node.ts`, `enable-queue-mode.md`)
